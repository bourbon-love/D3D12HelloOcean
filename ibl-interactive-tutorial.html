1为什么程序化天空能跳过 cubemap 光栅化

传统 IBL 管线把"捕获环境"当成拍六张照片：每个 cubemap 面都要重新设置视锥矩阵、绑定渲染目标、光栅化场景几何、逐像素着色。但本项目的天空 skyPS 其实是一个关于"观察方向 + 时间 + 天气"的纯函数——没有几何、没有光栅化，只有数学。这意味着"捕获"步骤可以直接退化成：对 cubemap 的每个 texel 算出它对应的方向向量，调用同一个函数求值，写进纹理。下面用 JS 重新实现了 EvalSkyRadiance() 的核心项（渐变 / 星空 / 太阳 / 月亮）， 拖动时间滑块，亲眼看看"它就是一个函数"是什么意思。

skyColor(dir, t) = gradient(dir.y) + stars(dir, t) + sunDisc(dir, sunDir(t)) + moonDisc(dir, moonDir(t)) + …
dir 是唯一的空间输入 — 不依赖任何顶点、三角形或渲染目标，cubemap texel 和穹顶像素问的是同一个问题

把两条管线摆在一起看：左边是传统光栅化捕获要做的事，右边是本项目实际要做的事。

✓无几何、无光栅化、无 RT 切换 — 一次 dispatch 搞定
天空根本没有"表面"可供光栅化——它从一开始就是一张关于方向的函数表。把这张表写进 cubemap，还是画在头顶的天空穹顶上， 调用的都应该是同一个 EvalSkyRadiance()；唯一变化的只是"谁在问方向"。这正是把它拆进 SkyCommon.hlsli 的意义所在——确保穹顶和 IBL 捕获两边问到的答案永远一致，也是 Phase A 的 SkyCaptureCS.hlsl 能直接跳过光栅化、退化成一次 compute dispatch 的根本原因。

2方向 ↔ cubemap 面 / UV 映射

SkyCaptureCS.hlsl 里的 FaceUVToDirection(face, uv) 把"面索引 + 面内 UV"转换成一个方向向量，供 EvalSkyRadiance() 求值。下面这个展开图做的是逆运算：给定一个方向，反推它落在 6 个面中的哪一个、以及在该面内的 UV 坐标—— 这正是验证 FaceUVToDirection 是否写对的方式（两者必须互为逆函数）。拖动方位角 / 仰角滑块，或点击预设方向，看方向向量"掉进"展开图里的哪一格。

face = argmax(|dir.x|, |dir.y|, |dir.z|)  // 哪个轴分量绝对值最大，方向就落在该轴对应的面上
uv = (面内另外两个分量) / 主导分量的绝对值  // FaceUVToDirection() 的逆运算 —— D3D 的 +X/-X/+Y/-Y/+Z/-Z 面顺序约定

3split-sum 近似：把一个积分拆成两半各自预算

IBL 的镜面环境光照本质上是"在整个半球环境光上对 BRDF 做积分"——逐像素实时算这种积分太贵了。Karis 的 split-sum 近似把它拆成两个可以 分别预先算好的部分：一半只跟"观察角度和粗糙度"有关，与具体材质、具体环境贴图都无关——这正是 BRDFLutCS.hlsl 一次性烘焙出来的这张 2D LUT； 另一半只跟材质的 F0（菲涅耳基础反射率）有关，运行时一行 F0 * scale + bias 就能算出来。拖动下面两个滑块，实时用 JS 重新实现 IntegrateBRDF()，和热力图（红 = scale 通道，绿 = bias 通道，正是实际 LUT 的 RG16F 编码）对照着看。

specular_IBL  ≈  prefilteredColor(R, roughness)  ×  ( F0 · scale(NdotV, roughness) + bias(NdotV, roughness) )
└── 环境部分：预滤波 cubemap（Phase C）──┘    └────── 这张 LUT：与材质无关，只烘焙一次 ──────┘   └ 材质部分：每像素 F0 ┘

这张 LUT 只有两个输入——NdotV 和 roughness——跟场景里有什么、天空长什么样、材质是什么完全无关，所以 IBLSystem::Init 只需要生成一次就能永久复用，是整条 IBL 管线里"预算得最彻底"的一环。 再看热力图本身：低粗糙度 + 高 NdotV（视线接近法线、表面接近镜面）的角落，(scale, bias) 迅速逼近 (1, 0)—— 这正是"正对镜面时反射率趋于 F0、掠射角时趋于 1"这一菲涅耳物理直觉，在数值上的直接体现。

4ローリングキャプチャ：6フレームで1枚を分散更新

每帧只写入 cubemap 的 1 个面，6 帧一轮回。可视化对比"每帧更新全部6面（朴素方案）"和"每帧仅更新1面（滚动方案）"的 GPU 调度开销差异。

这个优化之所以安全，是因为太阳和月亮移动极慢——完整昼夜周期长达数分钟， 6帧约 0.1 秒的陈旧度完全不可察觉。
若换成快速变化的光源（爆炸、快速旋转的聚光灯），这个技巧就不再成立—— 那种场景必须每帧更新全部 6 面，或改用预滤波球谐代替 cubemap。

5デバッグプレビューが証明すること — Phase A 総括

Phase A の「受け入れ基準」は ImGui のデバッグウィンドウ1枚。6面それぞれが正しい方向の空を捕らえていることを目視で確認する。

展開図（横十字）：各面が写すべきもの。赤枠 = 正しく確認できた面
✔ +Y 面（天頂）
昼：青い天空。夜：星野。正確なグラジエントが見えれば FaceUVToDirection の Y 軸は正しい。
✔ 太陽がいる面
太陽の輝点が in-game の方向と一致するか。回転・鏡像があれば case 0/4/5 の符号ミス。
✔ BRDF LUT
左下 (NdotV≈0, rough≈0) が暗く右上 (NdotV≈1, rough≈0) が明るいグラジエント。NaN/黒パッチなし。
Phase A でやったこと：
  1. 手続き型天空を純粋関数 EvalSkyRadiance に抽出（ラスタライズ不要）
  2. SkyCaptureCS でその関数を cubemap テクセルごとに評価してキャプチャ
  3. BRDFLutCS で split-sum BRDF 積分を一度だけ焼き込み
  4. 6フレーム分散更新でフレームコストを 1/6 に圧縮

Phase B/C でやること： この cubemap を 畳み込んで拡散・鏡面 IBL テクスチャを生成し、 海面・船体 PBR に F0 · scale + bias として足し込む—— データは正しく揃った。次はそれをライティングに使う。

6球面調和関数による拡散照度の畳み込み

Phase B の核心。キャプチャした cubemap を 9つのSH係数（SH9 = L0+L1+L2 = 1+3+5項）に畳み込む。 係数はコサインローブ積分済みなので、シェーダーでの評価は N だけの多項式になる。
